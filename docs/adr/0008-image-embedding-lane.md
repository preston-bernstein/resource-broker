# Image-embedding lane (Infinity / SigLIP)

**Status: accepted; implemented 2026-06-30 in `internal/proxy/NewEmbed`, `cmd/broker`, `internal/config`.**

The internal-scraper-service builds a durable image corpus and embeds each thumbnail with a frozen SigLIP model (its ADR 0013/0016) for similarity search. Ollama cannot serve SigLIP image embeddings (its embedding models are text-only), so a separate server is needed — [Infinity](https://github.com/michaelfeil/infinity) serving `google/siglip-so400m-patch14-384`. The question this ADR answers: how does that server fit the broker, which until now fronted exactly one Ollama upstream.

- **Why broker it at all.** The embedding server runs on **CPU**, not the GPU: the desktop GPU is an AMD RX 9070 XT (RDNA4/gfx1201) on ROCm 6.2, which Infinity's prebuilt ROCm image (MI200/MI300 only) does not support. So it never contends for VRAM. But it *does* contend for the **CPU/host** with gaming and Plex, and the scraper may run an embed/backfill pass outside the Friday lights-out window. The broker already computes the one signal that matters here — "gaming/Plex active, back off" (the yield controller) — so the lane subscribes to it and inherits 503-on-yield + cancel-in-flight for free. The scraper's embed client is fail-open (a 503 leaves the embedding NULL for a later pass), so back-off is lossless.

- **Own scheduler, shared yield.** GPU inference (Ollama) and CPU embedding use different hardware; forcing them through the single `MaxInflight` GPU slot would idle the GPU while the CPU embeds, halving scan throughput. The lane therefore runs on its **own `queue.Scheduler`** (its own `MaxInflight`, default 1 — Infinity already saturates every CPU core per request) while passing the **same yield `Controller`** as the Admission. Yield state is shared; the concurrency slot is not. The yield controller's Ollama-specific `Unload` is irrelevant to a CPU upstream and simply does nothing useful for it — harmless.

- **Path rewrite, stable consumer contract.** Infinity's unified OpenAI `POST /embeddings` tokenizes a base64 `data:` URI as **text** (every image returns a near-identical text-tower vector). Image embedding must target `POST /embeddings_image`. Rather than push that Infinity quirk into every consumer, the lane presents an OpenAI `/embeddings` (and `/v1/embeddings`) face and rewrites the path to `/embeddings_image` on the way to Infinity (`proxy.NewEmbed`); request and response bodies are untouched. Consumers keep the model-agnostic OpenAI wire contract, so the serving stack can change without consumer edits. Infinity runs with `--served-model-name siglip-so400m-patch14-384` so the model id the consumer sends (and stamps into its DB) matches the frozen identifier.

- **Optional.** The lane is started only when `INFINITY_URL` is set; unset, the broker behaves exactly as before. Listens on `BROKER_EMBED_ADDR` (default `:11438`).

We rejected: routing embeddings through the existing Ollama batch port (Ollama can't serve SigLIP); sharing the GPU scheduler (needless GPU/CPU serialization); teaching consumers Infinity's `/embeddings_image` path (leaks a serving-stack quirk into the stable contract); and a separate repo (Infinity is a stock container — the only code is this lane).
