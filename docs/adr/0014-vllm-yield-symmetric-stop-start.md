# Symmetric systemctl stop/start for vLLM yield-unload

**Status: accepted; implemented in `internal/yield/yield.go` (widened `Unloader` interface, `doReload`, and the `actionDone`/`startAction` handoff chain that orders `doUnload`/`doReload` across a flap), `internal/backend/openai_backend.go` (`systemdUnitController`, wired into `newOpenAIBackend`), `internal/ollama/client.go` (no-op `Reload`), `internal/config/config.go` (`UpstreamUnitName` / `UPSTREAM_UNIT_NAME`).**

ADR-0003 established the broker's hard-yield invariant for Ollama: when gaming/Plex contention appears, cancelling the in-flight request is not enough — the model must actually leave VRAM, or the game keeps starving. ADR-0004 puts that invariant under a scheduling policy where gaming always preempts inference. Neither ADR gave the openai-compatible backend (vLLM) any way to honor the invariant: `openaiBackend.Unloader()` returns a literal nil, so a vLLM upstream configured behind this backend keeps its model resident through contention today. This ADR closes that gap for operators who set `UPSTREAM_UNIT_NAME` to the systemd unit running their `vllm serve` process: on yield-start the broker runs `systemctl stop <unit>`, freeing VRAM immediately and leaving the unit down for the whole contention window; on yield-clear it runs `systemctl start <unit>`, bringing vLLM back up through its own normal startup path. This is the same shape as ADR-0003's Ollama unload/reload, just carried by systemd instead of an HTTP `keep_alive=0` call, and it sits under ADR-0004's preemption policy like every other yield action.

**Decision**: `yield.Unloader` gains a second method, `Reload(ctx context.Context) error`, alongside the existing `Unload`. `Controller.applyLocked` calls `doUnload` on yield-start and the new `doReload` on yield-clear — symmetric, not a single combined operation. The openai backend's concrete implementation, `systemdUnitController`, holds the configured unit name and a narrow command-runner seam (`func(ctx context.Context, verb string) error`, scoped to exactly "run systemctl `<verb>` `<this configured unit>`" — never a generic run-any-command primitive); `Unload` calls it with `"stop"`, `Reload` with `"start"`. An internal mutex on `systemdUnitController` ensures `Unload` and `Reload` for the same instance never run their systemctl commands concurrently — but that mutex alone cannot guarantee they run in the *order* the transitions happened, since `doUnload`/`doReload` are spawned as two independent goroutines with no ordering relationship between when they start executing. A fast yield-clear/yield-start flap could otherwise let a later `doReload`'s `start` win the race for the mutex and run before an earlier `doUnload`'s `stop`, leaving the unit stopped even though the controller's effective state is "not yielding". `Controller` closes that gap itself: each `applyLocked` transition hands the spawned `doUnload`/`doReload` a predecessor "done" channel (`actionDone`, set up by `startAction`) that it waits on before calling `Unload`/`Reload`, chaining every action strictly in transition order regardless of goroutine scheduling. `ollamaBackend`'s `Unloader` (`*ollama.Client`) gets a no-op `Reload` — Ollama's reload is implicit on its next `/api/generate` call, so there is nothing for this backend to do on yield-clear.

**Rejected: `systemctl restart`.** The original draft of this feature used a single `systemctl restart <unit>` on yield-start and did nothing on yield-clear, on the theory that "restart" reads as "unload and reload in one step." It doesn't. `restart` is stop-then-start bundled into one systemd job, run immediately, back to back — and `vllm serve` eagerly reloads its model and re-claims GPU memory at process startup, independent of whether the contention that triggered the yield is still active. The result: VRAM frees for a brief gap while the unit restarts, then the unit's own startup path re-occupies it seconds later, for the rest of the gaming session. That is exactly the "cancel-but-leave-loaded" failure mode ADR-0003 already rejected for Ollama — the restart mechanism just delays it by a few seconds instead of avoiding it. Symmetric stop/start avoids this because start is only ever issued from yield-clear, after contention has actually ended.

**Rejected: vLLM's `/sleep` + `/wake_up` API.** vLLM exposes an in-process sleep/wake API intended for exactly this kind of external VRAM-yield control, and it was the other candidate mechanism considered. It's rejected here because of an open, unresolved upstream bug, vllm-project/vllm#20627, reporting corrupted output on the OpenAI-compatible-server path after repeated sleep/wake cycles — precisely the repeated-cycle call pattern a contention-driven broker would produce over a long gaming session. Until that's resolved upstream, `/sleep`+`/wake_up` trades a systemd process boundary (which fully tears down and rebuilds vLLM's state on every cycle) for an in-process suspend that has a known correctness defect on the exact code path this feature would drive. `systemctl stop`/`start` has no equivalent risk: each start is a fresh process.

**Security scope**: this feature requires the broker's service account to run `systemctl stop`/`start` against a unit it doesn't own, which means a sudoers or polkit grant. That grant must be unit-specific — permitting exactly `systemctl stop <exact-unit>` and `systemctl start <exact-unit>`, never a wildcard such as `systemctl restart *` or `systemctl * vllm*`. The concrete risk of getting this wrong: `UPSTREAM_UNIT_NAME` is operator-set broker config, read at startup and passed straight into the command-runner's `<verb> <unit>` invocation with no unit-name syntax validation beyond whitespace-trimming. If the sudoers/polkit rule is ever misconfigured as a wildcard, that config value effectively controls what the broker's service account can stop and start on the host — a privilege-escalation surface this feature introduces. Closing it is a host-configuration responsibility (a scoped, exact-unit sudoers/polkit rule), not something the application code can enforce from inside the process.

**Accepted cost — connection-error window**: for the whole stopped/restarting window, consumer requests to the openai backend fail with connection errors. This is handled by the caller's existing retry/backoff (the same pattern already in place for Ollama unload — see ADR-0003); no new coordination, queuing, or request-buffering is being built for this feature.

**Rejected scope — startup preflight**: there is no active check, at broker startup or on config load, that the configured unit exists or that the sudoers/polkit rule is correctly scoped (e.g. no `systemctl show <unit>` probe). A misconfigured unit name or an unauthorized sudoers rule surfaces only on the first real yield event, as a failed `systemctl stop`/`start` logged at WARN. This is a deliberate scope cut, not an oversight: the failure is operator-visible on first occurrence and the alternative — an active preflight — adds a startup-time dependency on `systemctl`/D-Bus for a path that most deployments (no `UPSTREAM_UNIT_NAME` set) never exercise.

**Rejected scope — no new Prometheus metric**. Unload/reload outcomes on this path get no new metric or observability surface; they're WARN/INFO log lines only, same as the existing Ollama `doUnload` path. This is a deliberate decision for a lower-traffic, operator-configured feature, and it sits in tension with ADR-0013's precedent, which did add an observability surface (a new outcome label on `broker_requests_total`) for its per-request hot-path embed lane. That asymmetry is real, not accidental: ADR-0013's lane sees per-request traffic where a stuck call silently wedges a shared slot indefinitely, which justifies dedicated metrics; this feature fires only on contention transitions (rare, human-timescale events) and already logs each attempt, so a human reading logs after a reported problem is judged sufficient for now. If this path proves noisy or hard to diagnose from logs alone in practice, adding a metric is a cheap follow-up, not a redesign.

**Rejected scope — full unit-name validation**. Beyond `strings.TrimSpace` on `UPSTREAM_UNIT_NAME` (config.go), no further syntax validation of the unit name is performed. Full systemd-unit-name-grammar validation was considered and rejected as scope creep: the value is operator-set broker config, not user input, and a malformed name simply fails the `systemctl` call and logs an error — the same operator-visible failure mode as an unowned or nonexistent unit.

**Timeout caveat**: the shared per-call timeout in `yield.go` (`unloadReloadTimeout`, 30s, replacing the old Ollama-only 10s literal used by `doUnload` and now also `doReload`) is a client-side give-up bound only. `systemctl` talks to PID 1 over D-Bus; killing the `exec.CommandContext` process at timeout does not cancel the systemd job already queued. A `doUnload`/`doReload` call can log a timeout and return while the stop or start it requested completes — or keeps failing — asynchronously afterward, outside the broker's visibility.
