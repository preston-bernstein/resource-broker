# Every Synchronous request gets a correlation id, echoed and logged

**Status: accepted (2026-08-01 fleet observability audit); implemented 2026-08-01 in `internal/queue/gate.go`.**

The durable Job path has always had a correlation id — `j.ID` threads through every worker/service log line from submit to terminal state (`internal/job/worker.go`, `internal/job/service.go`). The Synchronous path (`:11435`/`:11436`/`:11438` — the overwhelming majority of traffic) had none at all: the access log carried only `class`, `outcome`, `wait_ms`, with no path, no method, no request identity. A Consumer (LightRAG, estate-scraper, fashion-monitor) that got a 503 or a slow response had no way to correlate its own failure with a specific Broker log line except by timestamp, and multiple concurrent requests from the same Consumer were indistinguishable from each other in the log stream.

`Gate` now mints an 8-byte hex id (`crypto/rand`, not `math/rand` — no shared-PRNG state to reason about, and the volume here is nowhere near where the cost would matter) at the top of admission, before the yield/park/acquire loop runs. It is echoed as an `X-Broker-Request-Id` response header (alongside the existing `X-Broker-Status` and `X-Broker-Wait-Ms`) so a Consumer can log it on its own side, and it is included — along with `path` and `method`, also previously absent — on both access-log call sites (the terminal "request" line in `Gate` and `deferRequest`'s 503 line). This gives the Synchronous path the same followability property the Job path already has: `grep req_id=<id>` finds every log line for one request.

This aligns with home-infra `CONVENTIONS.md` §18's correlation model: a per-request identifier is carried as structured log fields (`req_id`), never promoted to a Prometheus label or a Loki stream label — cardinality of one value per request would defeat both systems' indexing.

We rejected accepting an incoming `X-Request-Id` (or `traceparent`) header from the caller instead of always minting a fresh one — no current Consumer sends one, so honoring an absent header buys nothing today, and trusting a caller-supplied id as a log-correlation key without a namespacing scheme risks collisions between Consumers reusing the same ids. Revisit if/when a Consumer starts sending one (this ADR would then move to accept-and-fall-back-to-minted rather than always-minted). We also did not add `remote` (client address) or `upstream_ms` to the same log lines — those are real, further-narrowing audit suggestions but a separate, larger change to `Gate`'s timing instrumentation; tracked as a follow-up, not bundled into this id-only fix.
