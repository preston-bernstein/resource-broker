# Bounded upstream timeout on the embed lane

**Status: accepted; implemented in `internal/queue/gate.go` (`Gate`'s `upstreamTimeout` parameter), `internal/proxy/proxy.go` (`errorHandler`), `internal/config/config.go` (`BROKER_EMBED_TIMEOUT`), wired in `cmd/broker/main.go`.**

`Gate` bounds how long a request may **wait to acquire** the GPU/embed slot (`wait`, per class — `BROKER_INTERACTIVE_WAIT`/`BROKER_BATCH_WAIT`), but nothing bounded how long the request could **run once it held the slot**. The embed lane's own `Scheduler` (ADR-0008) has `MaxInflight` hardcoded to 1 (Infinity saturates all CPU cores per request). A stuck Infinity backend call — connection hangs, no response, no error — held that single slot forever: `next.ServeHTTP` never returned, so `defer s.Release()` (in `Gate`) never ran, and every request behind it queued for its full wait budget and then 503'd with "GPU busy: wait budget exceeded," indefinitely, until the process was restarted. This matches the live symptom Preston diagnosed on `:11438`.

**Decision**: `Gate` takes a new `upstreamTimeout time.Duration` parameter. When nonzero, the context passed to `next.ServeHTTP` is `context.WithTimeout(r.Context(), upstreamTimeout)` instead of the plain cancel-only context; when it fires, `next.ServeHTTP` returns (a well-behaved `http.Handler` — including `httputil.ReverseProxy`, which `internal/proxy.New`/`NewEmbed` both build on — observes context cancellation and returns), `defer s.Release()` runs, and the slot is freed for the next waiter. The outcome is recorded as `upstream_timeout`, distinct from `preempted` (yield) and `served`, so `/metrics`/logs can tell "the backend hung" from "gaming took the GPU" from "it worked."

**Scope, deliberately narrow**: `upstreamTimeout` defaults to `0` (disabled) everywhere except the embed lane. Interactive and batch requests to Ollama proper legitimately run for minutes (a long generation, a large batch scoring call) — imposing any fixed bound there would cut off correct, in-progress work, which is exactly the kind of thing ADR-0003/0004's yield-to-gaming law exists to prevent doing casually. Only `cmd/broker/main.go`'s embed-lane wiring passes a real value (`cfg.EmbedTimeout`, default `30s` via `BROKER_EMBED_TIMEOUT`) — chosen against ADR-0009's own numbers: embedding is documented there as "short-lived (< 1s per image)," so a multi-image batch completing well inside 30s leaves comfortable margin, and a call still running at 30s is behaving nothing like a normal request.

**Client-facing consistency**: `internal/proxy.errorHandler` already special-cased `context.Canceled` (yield/disconnect) as a `503` instead of the generic `502` used for real upstream faults. This ADR adds `context.DeadlineExceeded` to the same branch, and both now set `X-Broker-Status: deferred` and `Retry-After: 1` — the same signal shape `Gate`'s own `deferRequest` uses for every other deferral ("GPU busy: wait budget exceeded," "yielding GPU"). A client that already knows how to handle a `503` deferral from the Broker handles an upstream timeout identically, with no new code path to add.

**Rejected alternatives**:
- *A blanket timeout on every lane*: rejected — see the scope note above; this would silently truncate legitimate long-running interactive/batch generations, which is a correctness regression far worse than the bug being fixed.
- *Lowering `BROKER_MAX_INFLIGHT`/embed concurrency, or adding a second embed slot*: does not address the actual defect (a wedged request never returning) and would just let the wedge tie up a fraction of capacity instead of all of it — the request still never completes and never frees its slot.
- *A watchdog goroutine that force-closes the connection from outside `Gate`*: more moving parts than a `context.WithTimeout` the standard library already threads through `httputil.ReverseProxy` correctly; rejected as unnecessary complexity for the same outcome.
- *Retrying instead of timing out* (folding this into the existing `retryTransport`, see `internal/proxy/proxy.go`): retryTransport only retries a RoundTrip that already **failed** with a connection-level error before any bytes; it has no opinion on a call that neither fails nor returns. The two mechanisms are complementary, not overlapping: retry handles "the connection died," this ADR handles "the connection never dies or responds."

**Config**: `BROKER_EMBED_TIMEOUT` (default `30s`; `0` disables the bound, reverting the embed lane to the pre-ADR-0013 unbounded behavior). See README's config table and `deploy/broker.service`.

**Observability**: new outcome label `upstream_timeout` on the existing `broker_requests_total` metric family (same mechanism as `served`/`preempted`/`expired`/etc. — no new metric needed). Alert-worthy signal: `rate(broker_requests_total{outcome="upstream_timeout"}[5m]) > 0` — any nonzero rate means the embed lane hit a stuck backend call, which is exactly the failure this ADR exists to stop from being silent.
