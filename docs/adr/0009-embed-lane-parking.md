# Batch request parking during yield with FIFO release and hard ceilings

**Status: accepted; implemented 2026-07 in `internal/queue/park.go`, `internal/metrics`, `internal/config`, `cmd/broker/main.go`.**

When the Broker yields the GPU to gaming/Plex, Batch-class HTTP requests arriving during the yield window face three choices: (1) reject immediately with 503, (2) hold them in an in-memory queue and serve them when yield ends, or (3) make the choice configurable. This ADR accepts option 2: Batch requests that arrive during yield are **parked** in a bounded in-memory queue, released in FIFO order on a 1-second polling drain loop once yield ends, with hard ceilings on queue depth and hold time. Parking is **optional** (`BROKER_PARK_MAX_QUEUE=0` disables it), **bounded** (max queue depth, max hold time per request, fail-fast on shutdown), and **fail-closed** (existing behavior without configuration — today's immediate 503 on yield).

**Why now**: The embed lane (ADR-0008) and LightRAG research workloads generate bursts of batch embedding requests. An LLM research session repeatedly runs a corpus pass, embedding all items in one burst; rejecting the tail of that burst forces the client (LightRAG) to retry the whole batch, wasting completions. A 600-second hold bound (the default) lets the burst succeed within one Plex transcode session (typically 5–30 minutes) without risking stalled requests. Embedding is short-lived (< 1s per image), so the parking queue typically drains within minutes. The hard ceiling and configurable kill-switch satisfy NFR-3 and FR-5: no unbounded growth, no hidden resource leaks, and an operator can disable parking without a code change.

**Objections from ADR-0002 answered**: (C-3) *fd exhaustion*: parked requests are bounded by `BROKER_PARK_MAX_QUEUE` (default 32) and held for at most `BROKER_PARK_HOLD` (default 600s). The admission loop does not spawn goroutines or sockets per parked request; they block on a single channel in the parking struct. (C-1) *Timeout risk*: the 600-second hold is less than the 1200-second interactive-timeout margin documented in NFR-1 and NFR-2; clients expect at least that much jitter. (C-2) *Reboot safety*: park state is in-memory only (per NFR-4) and is not persisted. Parked requests are resolved within the 10-second graceful-shutdown window (FR-9): when shutdown is signaled, all parked requests fail immediately with a "crash_failed" outcome, the drain loop exits, and the Scheduler is torn down. On a hard crash, all parked requests are lost and must be retried by the client — recovery is delegated to the caller's resilience (LightRAG's rescan + cache, internal-scraper-service's retry).

**StartLimitBurst unchanged** (`StartLimitBurst=5`, `StartLimitIntervalSec=60` per ADR-0004). Some readers raised NFR-7: does parking increase the risk of thundering-herd startup? No. Parked requests are bounded and never trigger a panic by themselves; they enter the same `Scheduler.Acquire` path as any other request. A panic in the parking code (e.g. a logic error in the drain loop) is no worse than a panic in any other handler path — it would crash the Broker, same as today. The `StartLimitBurst` limit applies to *admission rate* (5 new requests per 60s), not queue depth; parking does not change this. If a park-path bug did create stalled requests that panicked at shutdown, the Broker would crash (unobservable to the client), but LightRAG rescan would recover.

**Release-order distinction**: FIFO governs the *order in which parked requests receive the release signal*, not the end-to-end order in which they are served. Once released from the park queue, a request re-enters `Scheduler.Acquire` and competes for the slot like any other. An interactive request may be admitted and served before a released batch request that was parked first (Interactive always preempts Batch). This is correct: parking is only about *not rejecting* Batch during yield; it does not change priority order.

**Scope notes**: Parking applies only to Batch-class synchronous requests that arrive during yield. Job submissions via `/jobs` remain stateless per ADR-0002/0006 (a Job is persisted immediately and never parked). Interactive requests are never parked (Interactive waits on the slot, not in a park queue). The Ollama upstream path is unchanged; parking is only in the admission gate, before Ollama. Embed-lane (ADR-0008) has its own scheduler and is not covered by this ADR (scope limited to GPU-contention yield; embed lane's backoff is via the yield controller's 503 on yield, not parking).

We rejected: unbounded queues (no ceiling, violates NFR-3); `sync.Cond` signaling from `yield.Controller.Yielding()` (adds a new Admission method `YieldEnd()` and complex wiring; simpler to poll every 1s); a separate `internal/park` package (parking is an admission-loop concern, not generic infrastructure); token-bucket algorithms for release (FIFO is simpler and meets the SLA); and a separate `BROKER_PARK_ENABLED` toggle (0 already kills it; a separate flag is noise).

**Observability**: live queue depth is `broker_parked_depth` (also on `/status` as `parked`); time-in-park is `broker_park_wait_seconds_sum/_count`; outcomes ride the existing `broker_requests_total` family (`expired`, `park_rejected`, `canceled`, `crash_failed`). The alert-worthy signal is `rate(broker_requests_total{outcome="expired"}[5m]) > 0` — parks aging out means yield windows are outlasting `BROKER_PARK_HOLD`.
