# HTTP path is stateless: bounded wait then 503, consumers own retry

**Status: still in force for Synchronous requests (interactive + short batch); superseded for long batch by ADR-0006/0007, which add a durable async Job path.** The stateless model proved too weak once many services and long, resilience-critical workloads (multi-item scoring, vision) needed position/status feedback and restart survival — see ADR-0006.

An HTTP caller cannot hold an open connection through a multi-hour gaming session, so the Broker does not durably queue HTTP requests. Each request waits in an in-memory queue for a per-class budget (interactive longer, batch short); if it is not served within budget — or arrives while the Broker is yielding — it returns `503` with `Retry-After`. The Broker therefore holds nothing across restarts and is trivially reboot-safe. This works because every consumer already tolerates a deferred LLM: internal-monitor-app's `PENDING` score state replays listings on the next healthy run, and LightRAG / internal-scraper-service retry. We rejected holding connections until served (file-descriptor leaks, client timeouts fire anyway) and a durable SQLite request queue (an HTTP request/response cannot be replayed after the caller's connection is gone). The durable file-based queue survives only for the legacy CLI fire-and-forget job path, which is decoupled from the HTTP proxy.
