# Plan: Idle-unload for openai-compatible (vLLM) backend instances

## Approach

Idle is a second *event source* into the exact same `yield.Controller` per-instance `actionDone` machinery that Contention already drives (ADR-0014/ADR-0015) — never a second controller, timer goroutine, or unload mechanism. The Idle-check runs inside the Controller's existing `refresh()` tick (same goroutine, same `c.mu` critical section, right after the Contention `applyLocked()` call), so Idle-vs-Yield ordering is resolved by construction rather than by a new synchronization primitive. Per-instance "last dispatch" and "in-flight" state is tracked with a small set of lock-free atomics on `Controller` itself, populated by a thin `http.Handler` decorator wrapped around each idle-configured instance's `Proxy()` at construction time in `cmd/broker/main.go` — `Router`, `Gate`, and the Job worker stay completely unaware the feature exists. Every instance with no Idle duration configured is never wrapped and never checked beyond one cheap `continue`, satisfying FR16/AC1 exactly.

## Architecture

```
                         DetectInterval ticker (existing, unchanged)
                                   │
                              Controller.Run
                                   │
                              c.refresh()                       [same goroutine as today]
                                   │  c.mu.Lock()
                    ┌──────────────┴───────────────┐
                    │                               │
            c.applyLocked()                 c.checkIdleLocked()   [NEW — runs 2nd,
        (Contention: unchanged           same lock, same tick]
         except doUnload/doReload
         now reset lastDispatch/
         idleUnloaded on yield-clear,
         FR13)                          for each configured instance i:
                                           skip if c.effective (FR10/AC6)
                                           skip if idle disabled (idleTimeouts[i]==0)
                                           skip if inFlight[i] > 0 (FR12/AC8)
                                           skip if already idleUnloaded[i]
                                           skip if now-lastDispatch[i] < idleTimeouts[i]
                                           else: CAS idleUnloaded false->true,
                                                 startAction(i), go doUnload(i,...,triggerIdle)
                    │                               │
                    └──────────────┬────────────────┘
                              c.mu.Unlock()

Request path (per configured instance i with idle enabled only):
  Gate → interactiveProxy/batchProxy → [Router.resolve →] Backend.Proxy()
                                              │
                              *activityBackend.Proxy() returns the SAME
                              wrapped http.Handler on every call — built
                              exactly ONCE, at construction time, inside
                              WithActivityTracking(b, ctrl, origIdx)'s own
                              body:
                                realHandler := b.Proxy()
                                wrapped := ctrl.TrackActivity(origIdx, realHandler)
                              never rebuilt per request
                                              │
                    on start: inFlight[idx]++, lastDispatch[idx]=now
                              if idleUnloaded[idx] CAS true->false:
                                  startAction(idx); go doReload(idx,...,triggerIdle)   [FR13, AC5]
                                              │
                                    next.ServeHTTP (the real proxy call)
                                              │
                    on end (deferred, registered right after the increment
                    so it runs even if next.ServeHTTP panics):
                              inFlight[idx]--, lastDispatch[idx]=now
```

**Same goroutine, extended, not a second poller.** `checkIdleLocked()` is called directly from `refresh()`, immediately after `applyLocked()`, inside the same `c.mu` critical section, in the single goroutine `Run` already owns. This is the cheapest and most-obviously-correct composition: FR8 already asks for "the existing detector poll loop cadence... following the polling shape `yield.Controller.Run` already uses," and running Idle-checks strictly after Contention-checks in the same lock means `checkIdleLocked` always observes the *post-transition* `c.effective` value for this tick — there is no window where a second goroutine could observe stale Contention state and race a decision against it. The Contention transition's own `Unload`/`Reload` goroutines are spawned (not run) inside `applyLocked`, so the few extra atomic reads `checkIdleLocked` performs afterward add no observable latency to the Yield transition itself (NFR: "never delay... a Contention-triggered Yield transition").

**Where "last dispatch" and "in-flight" live, and why no data race.** They live on `Controller` itself, not on `Router` or `openaiBackend` — four new parallel slices, index-aligned with the pre-existing `c.unloaders`/`c.labels`/`c.actionDone` (i.e. the *post-nil-filter* index space `NewWithConfirmMulti` already builds):
- `idleTimeouts []time.Duration` — 0 means disabled for that instance.
- `lastDispatch []atomic.Int64` — UnixNano of the most recent dispatch start/end.
- `inFlight []atomic.Int32` — concurrent in-flight request count.
- `idleUnloaded []atomic.Bool` — true while VRAM is currently idle-freed for that instance.

Only `Controller` mutates them, and every mutation is either (a) a plain atomic store/add from the request-tracking handler (no lock — the hot request path must not contend on `c.mu`), or (b) a read inside `checkIdleLocked`, which already holds `c.mu` for the Contention check anyway. The one place these two writers could genuinely race — a new request arriving for an instance in the same instant `checkIdleLocked` is deciding whether to fire — is resolved by `atomic.Bool.CompareAndSwap` on `idleUnloaded`: whichever side's CAS lands first wins that instant, and the *loser* is not stranded — a `checkIdleLocked` fire that loses the race to an arriving request simply never happens (the CAS fails, `continue`); a wake-reload that loses to a firing idle-unload still runs, chained strictly after the unload via the shared `actionDone[i]`/`startAction(i)` handoff (see below), so the net result is always well-ordered stop-then-start, never a stray start-then-stop.

**How Idle-fire and Contention-fire for the same instance resolve to at most one net effect (FR11/AC7).** Both sources reach VRAM control exclusively through `startAction(i)`/`actionDone[i]` — the identical ADR-0014 predecessor-completion chain Contention alone used before this feature. Two cases:
1. *Idle about to fire the same tick Contention begins*: `checkIdleLocked` runs strictly after `applyLocked` in the same `refresh()` call, so it always sees `c.effective == true` already and skips entirely (FR10). Only the Contention-triggered `Unload` fires. Zero duplicate calls.
2. *Idle already fired in an earlier tick (`idleUnloaded[i]==true`), Contention begins later*: `applyLocked`'s existing all-instance `Unload` loop fires again for instance `i` unconditionally (it does not know or care about Idle's per-instance state, by design — Contention's response must never depend on Idle bookkeeping). This is a second `systemctl stop` on an already-stopped unit — idempotent at the systemd level, and still strictly ordered after Idle's own `Unload` by the shared `actionDone[i]` chain, so it is never a *conflicting* pair (no `Unload`+`Reload` racing out of order) — the one property FR11 actually calls out as unacceptable. This is documented here explicitly as the one case where two `Unload` calls can legitimately occur; it is a deliberate, reasoned acceptance (Contention's response must stay dead simple and instance-idle-agnostic — see ADR-0004's absolute-priority invariant), not an unresolved race.
3. *Idle-wake (new request arrives on an idle-unloaded instance) races a Contention transition*: same mechanism — both paths call `startAction(i)` while holding `c.mu` (the request-path wake branch takes `c.mu` only for this rare CAS-won case), so the two `doUnload`/`doReload` goroutine spawns are strictly ordered by whichever acquired `c.mu` first, and each new action always waits on its chained predecessor's `done` channel before calling `Unload`/`Reload` — the existing ADR-0014 guarantee, unmodified, now generalized to a third caller.

**Construction order in `cmd/broker/main.go`'s routes branch (critical — do not get this wrong).** `Router.def` and each route's backend (`routeBackends[i]`) are plain Go interface values copied BY VALUE into the `Router` at `backend.NewRouter(be)` / `r.AddRoute(model, rb.Lane, routeBackends[i])` construction time — the router keeps its own copy of whatever `be`/`routeBackends[i]` were at that instant. In the current (pre-this-feature) code, the routes branch of `main()` constructs `r := backend.NewRouter(be)` and runs the `AddRoute` loop, and only afterward builds `unloaders`/`labels` and constructs `ctrl` via `yield.NewWithConfirmMulti`. If Idle's activity-tracking decoration (`be = backend.WithActivityTracking(be, ctrl, 0)` etc.) is applied to the local `be`/`routeBackends[i]` variables after that point — as a naive "add `ConfigureIdle` + decorate after `ctrl` exists" edit would do — reassigning those local variables does **not** change what `NewRouter`/`AddRoute` already copied into `router`. The router permanently holds the undecorated backends: for a routed vLLM instance with Idle-unload configured, `TrackActivity` would never observe live routed traffic, so that instance would idle-unload while actively serving requests and never wake back up via `TrackActivity` (only a Contention-triggered `Reload` or a full broker restart would ever bring it back). This is a real, silent production bug for the exact topology this feature targets, and must not ship.

The routes branch must therefore be restructured so `ctrl` is constructed, and `be`/`routeBackends[i]` are decorated, BEFORE `backend.NewRouter(be)` and the `AddRoute` loop run. Corrected construction order for the `len(cfg.Routes) != 0` branch:
1. `routeBackends, routeUnloaders, labels, err := buildRoutes(cfg)` (unchanged, already first).
2. `unloaders := append([]yield.Unloader{be.Unloader()}, routeUnloaders...)`; `labels = append([]string{"default"}, labels...)` (moved up — unchanged content, just earlier).
3. `ctrl = yield.NewWithConfirmMulti(detector, unloaders, labels, cfg.DetectInterval, cfg.YieldConfirmPolls)` (moved up).
4. `ctrl.ConfigureIdle(...)` with an orig-index-ordered slice: `[cfg.UpstreamIdleTimeout, cfg.Routes[0].IdleTimeout, cfg.Routes[1].IdleTimeout, ...]`.
5. Decorate in place — orig-index 0 is the default backend, orig-index `i+1` is `cfg.Routes[i]`: `if cfg.UpstreamIdleTimeout != 0 { be = backend.WithActivityTracking(be, ctrl, 0) }`; then for each route `i`, `if cfg.Routes[i].IdleTimeout != 0 { routeBackends[i] = backend.WithActivityTracking(routeBackends[i], ctrl, i+1) }`.
6. Only now: `r := backend.NewRouter(be)` (using the possibly-decorated `be`), then the `AddRoute` loop — `for i, rb := range cfg.Routes { for _, model := range rb.Models { r.AddRoute(model, rb.Lane, routeBackends[i]) } }` (using the possibly-decorated `routeBackends[i]`).
7. `router = r; activeBackend = router` (unchanged).
8. The `routeSummary`/`slog.Info("routing configured", ...)` logging (unchanged, order-independent).

The no-routes branch (`len(cfg.Routes) == 0`) needs no restructuring: `ctrl = yield.NewWithConfirm(...)` already runs first in that branch, and `be` is not consumed until later (`be.Proxy()` at the `interactiveProxy`/`batchProxy` construction, well after this branch) — so adding `ctrl.ConfigureIdle(...)` and `if cfg.UpstreamIdleTimeout != 0 { be = backend.WithActivityTracking(be, ctrl, 0) }` immediately after constructing `ctrl` in that branch is correct as originally described, no reordering needed there.

## Data model

No data model changes. (No SQLite schema touched — Idle state is in-memory only, matching Contention's own in-memory `Controller` state; a broker restart re-initializes every instance's idle clock to "just started," see Risk areas.)

## API / interface contract

**New environment variables** (flat scalar, `getenv`/`getdur` idiom, matching `BROKER_BATCH_QUANTUM`):
- `UPSTREAM_IDLE_TIMEOUT` (default unset/empty = disabled) — Idle duration for the default backend. Parsed with `getdur` (hard-fail at `Load()` on a malformed value), the same fail-loudly posture as `BROKER_BATCH_QUANTUM`, resolving the NFR's open question: this is required-shape operator config, not a resilience-layered value like Park's, so it gets `getdur`, not `getdurWarn`.
- `BROKER_ROUTE_<N>_IDLE_TIMEOUT` (default unset/empty = disabled) — per-route Idle duration, same parsing, independent per route.
- **Validation (FR5/AC9, in `config.Load()`)**: `UPSTREAM_IDLE_TIMEOUT` set and non-zero while `UPSTREAM_UNIT_NAME` is empty fails `Load()` with a descriptive error; same check per-route (`BROKER_ROUTE_<N>_IDLE_TIMEOUT` set while `BROKER_ROUTE_<N>_UNIT_NAME` is empty fails `Load()`), added inline in the existing per-route validation loop alongside the existing `LANE`/`UNIT_NAME` checks. See the `internal/config/config.go` Integration point below for exactly where the checks go, given `UPSTREAM_UNIT_NAME` is read in two places in the real file today.

**`/status` — new optional `"idle"` key**, same conditional-inclusion pattern as `"routing"`/`"tdarr"` (present only when at least one instance has Idle-unload enabled; entirely absent otherwise, preserving AC1's byte-for-byte-identical requirement):
```json
"idle": [
  {"label": "default", "idle_timeout": "1h0m0s", "idle_unloaded": false, "since_last_dispatch": "12m4s"},
  {"label": "http://127.0.0.1:8001", "idle_timeout": "20m0s", "idle_unloaded": true, "since_last_dispatch": "37m0s"}
]
```
Only instances with Idle actually configured appear (AC11).

**`IdleSummary()`'s nil-vs-non-empty contract (pinned down precisely, not left ambiguous)**: `IdleSummary()` returns `nil` **only** when zero instances have Idle-unload configured at all — in that case `main.go`'s `idleStatus func() any` is itself nil, so `/status`'s conditional-inclusion wrapper omits the `"idle"` key entirely, preserving AC1's byte-for-byte guarantee. `IdleSummary()` returns a **non-nil, and therefore always non-empty** (it exists at all only because at least one instance is configured) slice whenever at least one instance has Idle-unload enabled, regardless of whether any instance is currently idle-unloaded. There is no code path where `IdleSummary()` returns a non-nil empty slice, and no test should treat "nil or empty" as equally acceptable — only one of those two shapes is correct for a given input.

**Log lines (FR14/AC10)** — existing `doUnload`/`doReload` WARN/INFO lines gain a `trigger` field, typed as the new `unloadTrigger` string alias (`triggerYield`/`triggerIdle` — see Integration points), e.g. `slog.Info("vram unload requested", "instance", label, "trigger", string(triggerIdle))`, grep-distinguishable from a Contention-sourced line (`trigger=yield`).

No new HTTP endpoints, no new CLI flags, no changes to `/control` or `/healthz`.

Otherwise store `idleTimeouts[i]` at `c.idleTimeouts[post]`.
  - New exported `TrackActivity(origIdx int, next http.Handler) http.Handler` — the request-tracking decorator. Looks up `post := c.origToFiltered[origIdx]` once, at call time (i.e. once, at `WithActivityTracking`'s wrap-time call — see the `internal/backend/activity.go` bullet below, never per-request), and panics immediately with a clear message if `post == -1` (same invariant-violation posture as `ConfigureIdle`) rather than indexing `idleTimeouts`/`lastDispatch`/`inFlight`/`idleUnloaded` out of bounds. The returned `http.Handler`, on every invocation: increments `inFlight[post]` and sets `lastDispatch[post]=now`; if `idleUnloaded[post]` CAS-transitions true→false, calls `startAction(post)` and spawns `go c.doReload(post, wait, done, triggerIdle)` (FR13/AC5) before calling `next.ServeHTTP`; then calls `next.ServeHTTP`. The `inFlight[post]` decrement **must be a deferred call** (`defer c.inFlight[post].Add(-1)`), registered immediately after the increment — not a plain statement after `next.ServeHTTP` returns — so it unconditionally runs even if `next.ServeHTTP` panics or returns early. An un-decremented `inFlight` counter permanently misrepresents that instance's in-flight state to `checkIdleLocked`'s `skip if inFlight[i] > 0` check, which is exactly the kind of silent, hard-to-notice bug a deferred decrement avoids entirely.

## Technology choices

- `sync/atomic`'s typed wrappers (`atomic.Int64`, `atomic.Int32`, `atomic.Bool`, all in the standard library, Go 1.24 per `go.mod`) — chosen over guarding `lastDispatch`/`inFlight` with `c.mu` so the per-request hot path (`TrackActivity`'s common case) never contends on the Controller's existing lock, which also guards Contention's own state. No new dependency.
- Go decorator pattern via interface embedding (`activityBackend{ Backend; proxy http.Handler }`) — chosen over adding a new method to the `Backend` interface (which would force every implementation, including `Router`, to grow a no-op) or threading tracking calls into `openaiBackend`/`Router` directly (which would couple two packages that today only depend on `yield.Unloader`'s narrow type, not `*yield.Controller` itself). This is the same "narrow wrapper" idiom `systemdUnitController`'s `run` seam and `Router`'s `AddRoute` already use.
- Rejected: consolidating the Controller's now-8 parallel index-aligned slices (`unloaders`, `labels`, `actionDone`, plus the 5 new idle-tracking fields — `idleTimeouts`, `lastDispatch`, `inFlight`, `idleUnloaded`, `origToFiltered`) into a single `[]instanceState` array-of-structs. Kept as parallel slices to match every existing field on `Controller` and avoid a mixed style within one struct; acknowledged as the same risk profile ADR-0015 already flagged for this file, not a new one — a future feature adding a 9th/10th parallel field is a reasonable trigger to revisit this as a single array-of-structs refactor.

## Risk areas

- **Job-path (`Generate`) dispatches never reset the idle clock.** FR6 explicitly scopes "last dispatch" to "the same per-instance resolution `Router.resolve` / the default backend's proxy already perform" — i.e. the Synchronous proxy path only. A deployment routing a model to an openai-compatible instance used *exclusively* via the durable Job path (no Synchronous traffic) would have that instance idle-unloaded mid-Job-stream-of-work even while genuinely busy, since `job.NewWorker`'s `Generate` calls never touch `TrackActivity`. This matches the letter of the requirements as written, but is worth flagging: if this proves to be a real desktop workload shape, `Generate`'s call sites (`openaiBackend.Generate`, `Router.Generate`) would need the same tracking wrapped in, which the current design does not do.
- **Broker-restart resets every instance's idle clock to "process start," not "true last real usage."** `lastDispatch` is in-memory only (no data model changes, by design) and is initialized to `time.Now()` at `Controller` construction. A restart immediately after a long-idle instance was last used gives that instance a full fresh idle window rather than picking up where it left off — never a correctness bug (worst case: VRAM sits loaded a bit longer than the configured timeout after a restart), but an operator watching `/status`'s `since_last_dispatch` right after a broker restart will see it reset to ~0, which is a mildly surprising but intentional and low-cost trade-off (avoiding a new persistence path for one non-critical timestamp).
- **Two `Unload` calls can occur for the same instance in the documented Idle-then-Contention sequencing case** (Architecture, case 2) — deliberately accepted as idempotent-and-harmless rather than added complexity to make Contention's own unconditional-unload-all-instances loop Idle-state-aware. If a future `systemd` version or unit type ever makes a redundant `stop` non-idempotent (unlikely, but not something this plan verifies against the real unit type in use), this assumption should be re-checked.
- **`checkIdleLocked`'s atomic reads happen inside `c.mu` while `TrackActivity`'s writes happen outside it** — correct per Go's happens-before rules for atomics (no data race), but it is a genuinely less obvious concurrency shape than "everything behind one mutex," and a future contributor extending this code without reading the `actionDone`/atomics doc comments could introduce a real race by, e.g., changing `lastDispatch` to a plain (non-atomic) field for convenience. This risk is mitigated the same way ADR-0014's own ordering gap was — dense doc comments on the fields themselves — but is worth calling out as the single most failure-prone spot in this design for a future edit.
- **`admin.Mux`'s signature change requires updating every existing call site** (`cmd/broker/main.go` and `internal/admin/admin_test.go`) — mechanical, low risk, but is the one place this plan does *not* preserve "existing tests pass unmodified" (AC12 scopes that guarantee to `internal/yield` and `internal/backend` only, not `internal/admin`, so this is in-scope to edit, not a violation).
- **Idle-triggered wake is fire-and-forget, same as Contention's own wake, and is an accepted cost, not a new design element.** `TrackActivity`'s CAS-won wake branch spawns `doReload` and calls `next.ServeHTTP` immediately, without waiting for the reload to complete — the waking request (and any other requests arriving during vLLM's cold-start window that follows) will likely get connection errors against the still-down upstream. This mirrors ADR-0014's own "accepted cost — connection-error window" framing for Contention-triggered unloads, handled by the same existing caller retry/backoff Consumers already build against Contention's identical behavior; it is restated explicitly here because Idle is a new trigger source, not because it needs new handling.
- **Revisit vLLM's native `/sleep`+`/wake_up` API for the Idle trigger specifically, later, once vllm-project/vllm#20627 closes upstream.** ADR-0014 rejected vLLM's native sleep/wake mechanism in favor of `systemctl stop`/`start`, citing that open upstream bug in repeated sleep/wake cycling. That rejection was made against Contention's usage pattern (rare, gaming-session-triggered); Idle-unload's expected fire-frequency is materially higher (routine usage gaps during normal operation), closer to the repeated-cycle pattern #20627 actually affects, so ADR-0014's mechanism-rejection rationale should be re-examined specifically for the Idle trigger once that bug closes. `systemctl stop`/`start` remains the correct choice today — this is a hard constraint, unchanged by this plan.
- **No hysteresis — a workload with usage gaps landing near the configured Idle timeout will thrash**, each unload/reload cycle paying full cold-start cost. This is a known operator-tuning consideration (configure `UPSTREAM_IDLE_TIMEOUT`/`BROKER_ROUTE_<N>_IDLE_TIMEOUT` meaningfully larger than expected usage gaps), not a defect this feature's initial version addresses — flagged explicitly here rather than left for an operator to discover the hard way, matching this repo's existing practice of documenting known accepted costs (see ADR-0014).
- **No new Prometheus metric for Idle-unload events**, matching ADR-0014's own precedent for Contention-triggered unload/reload (logs only, no counter). Given the thrash risk above is currently only log-visible, a per-instance idle-fire/idle-wake counter would be a cheap, additive follow-up if thrash symptoms are reported in production — same "cheap follow-up, not a redesign" framing ADR-0014 already uses for its own no-metric decision.
- **`docs/adr/0016-vllm-idle-unload.md` is in scope for this plan's own implementation**, not an unimplemented follow-up — it should record the "same goroutine, atomics on Controller, decorator on Backend, `origToFiltered` mapping, and the FR11 two-Unload carve-out" decisions, matching this repo's established one-ADR-per-yield-decision convention (0003/0004/0013/0014/0015). steps.md gets its own step for actually writing it; this plan only records that it is now in-scope.
