# Requirements: OpenAI-Compatible Upstream Backend

## Problem statement

The Broker's Fronting Proxy (`internal/proxy/proxy.go`) and Job worker (`internal/job/worker.go` via `internal/ollama/client.go`) both speak Ollama's native HTTP API exclusively, and both hardcode a single upstream target (`OLLAMA_URL`). This couples every Consumer-facing behavior the Broker provides — Yield/priority admission, durable Jobs, parking, `X-Broker-*` observability, `/healthz` — to Ollama as the only inference engine the Broker can front. Preston wants to run vLLM instead of (or alongside) Ollama on the shared GPU, because [reason: e.g. model support, throughput — TBD], but cannot today without either forking the Broker's proxy/job logic or forcing every Consumer to speak a second protocol. This matters now because the GPU-arbitration logic (Yield, priority, durability) is upstream-agnostic in principle but not in code, and duplicating it per-backend would create two codepaths to keep in sync. This feature generalizes "upstream" to a pluggable backend so a future vLLM cutover is a config change, not a rewrite — while leaving today's Ollama-only behavior completely unchanged by default.

## Users / stakeholders

- **Consumers** (internal-monitor-app, LightRAG, internal-scraper-service, one-off CLI jobs) — must see zero behavior or wire-contract change regardless of which backend is configured; they continue speaking Ollama's API to the Broker.
- **Broker operator** (Preston) — configures `UPSTREAM_BACKEND` and the corresponding upstream URL; needs the switch to be a config-only change with no code edits per deployment.
- **Broker maintainers** (future Claude Code sessions working this repo) — need the backend abstraction to be a single seam so Yield/priority/Job/observability logic isn't duplicated per backend.
- **Home GPU** (shared with gaming/Plex, out of this feature's control) — indirectly affected: whichever backend is selected must still fully respect Yield/preemption so gaming and Plex are unaffected.

## Functional requirements

1. The system shall provide a `Backend` abstraction that both the Fronting Proxy path (Synchronous requests) and the Job worker path (`internal/job/worker.go`'s `Generator` interface) call through, so no call site branches on which upstream API family is configured.
2. The system shall support exactly two `Backend` implementations at ship time: `ollama` (wraps the existing native-Ollama pass-through/client behavior unchanged) and `openai` (translates to/from an OpenAI-compatible upstream).
3. The system shall select the active backend via a new `UPSTREAM_BACKEND` environment variable with allowed values `ollama` and `openai`, validated at config load (`internal/config/config.go`'s `Load()`), failing startup with a descriptive error on any other value.
4. The system shall default `UPSTREAM_BACKEND` to `ollama` when unset, reproducing today's exact behavior with zero config changes required for existing deployments.
5. The system shall add a new config field for the OpenAI-compatible upstream base URL (e.g. `UPSTREAM_URL`, placeholder name — final name TBD), parsed and validated the same way `OLLAMA_URL` is validated today (must include scheme and host), required only when `UPSTREAM_BACKEND=openai`.
6. When `UPSTREAM_BACKEND=openai`, the system shall translate a Consumer's Ollama-shaped chat/generate request (`/api/generate` and/or `/api/chat`, per whichever the Fronting Proxy accepts today) into the OpenAI-compatible upstream's chat completions request shape, and translate the upstream's response back into the Ollama response shape the Consumer expects (including the streaming NDJSON chunk format), so the Consumer requires no code change.
7. When `UPSTREAM_BACKEND=openai`, the system shall translate a Consumer's Ollama-shaped text-embeddings request translation (`/api/embed`) — distinct from the image-embedding embed lane (`INFINITY_URL`, ADR-0008), which is out of scope — into the OpenAI-compatible upstream's `/embeddings` request shape, and translate the response back into the Ollama embeddings response shape. The order of embedding vectors in the response array shall correspond to the order of inputs in the request.
8. The system shall preserve streaming behavior for chat/generate under the `openai` backend: response tokens/chunks shall be flushed to the Consumer as they arrive (no full-response buffering), matching the Fronting Proxy's existing `FlushInterval: -1` streaming guarantee.
9. The system shall preserve Job-path chat/generate behavior under the `openai` backend: `internal/ollama/client.go`'s `Generate` (or its backend-abstracted equivalent) shall report a running token count via `onTokens` as chunks arrive, sourced from the OpenAI-compatible upstream's streaming response, so Job progress reporting is unaffected. The counted tokens feed into the Broker's existing Job progress-reporting mechanism, already externally observable via `GET /jobs/<id>` and the SSE `/jobs/<id>/events` stream per the existing Job system, unchanged by this feature.
10. The system shall map an OpenAI-compatible upstream error response (non-2xx status, or a mid-stream error event) to the same error handling the Ollama backend produces today (`ollama /api/generate: status %d`-equivalent, or `ollama: %s`-equivalent for a streamed error field) so callers of `Generator.Generate` see one consistent error contract regardless of backend.
11. The system shall preserve all existing Yield/Contention behavior unchanged under either backend: a Yield in progress shall cancel in-flight requests to whichever backend is configured via the same `ServeContext()` cancellation path, and no request shall be admitted to either backend while yielding.
12. The system shall preserve interactive-over-batch priority and Job preemption (`internal/job/worker.go`'s `monitor`/`shouldPreempt`) unchanged under either backend — preemption is a property of the Gate/scheduler, not the backend, and must not require backend-specific logic.
13. The system shall preserve the full durable Job lifecycle (QUEUED → RUNNING → SUCCEEDED | FAILED | CANCELED, restart survival, retry up to `BROKER_JOB_MAX_ATTEMPTS`, requeue-to-front on preemption) unchanged under either backend.
14. The system shall preserve Parking behavior (`BROKER_PARK_*` config, drain burst, expiry) unchanged under either backend — parking operates on Synchronous batch requests ahead of the backend call, independent of which backend eventually serves them.
15. The system shall preserve the `X-Broker-Request-Id`, `X-Broker-Wait-Ms`, and `X-Broker-Status` (header and trailer) contract unchanged under either backend, including the `served`/`deferred`/`preempted` outcome values.
16. The system shall extend `/healthz`'s upstream-reachability check to probe whichever backend is currently configured (the `ollama` backend's existing reachability check when `UPSTREAM_BACKEND=ollama`; an equivalent reachability probe against the OpenAI-compatible upstream's health/models endpoint when `UPSTREAM_BACKEND=openai`), so `/healthz` continues to name the correct failed dependency for either configuration.
17. The system shall preserve `/healthz`'s other two checks (job store readable, detector loop alive) unchanged and independent of backend selection.
18. The system shall not translate or forward the image-embedding embed lane (`internal/proxy.NewEmbed`, `INFINITY_URL`, ADR-0008) through the new backend abstraction — that lane keeps its own separate upstream and code path untouched by this feature, and is unrelated to this feature's text-embeddings request translation (`/api/embed`, FR-7).
19. The system shall preserve the Ollama-native `Unload`/`LoadedModels` VRAM-management calls (`internal/ollama/client.go`) as `ollama`-backend-only behavior; the `openai` backend shall not attempt an equivalent call and shall document (via code comment and this spec's Out of scope) that VRAM unload-on-yield is Ollama-specific.
20. The system shall be testable end-to-end against a mock/stub OpenAI-compatible HTTP server for both the chat/generate translation and the text-embeddings translation, without requiring a real vLLM (or other real OpenAI-compatible) server to be running.
21. The system shall preserve existing Ollama-backend request/response translation as a no-op passthrough — i.e., selecting `UPSTREAM_BACKEND=ollama` shall produce byte-identical request/response handling to the pre-feature code path (verified by the existing test suite passing unmodified against the `ollama` backend).
22. The system shall route requests through the identical code path that existed before this feature when `UPSTREAM_BACKEND=ollama`: request handling shall invoke the same `proxy.New()`-constructed `httputil.ReverseProxy` used pre-feature, with no added translation or dispatch layer interposed on that path. This shall be verified structurally — via a code-path or type assertion in tests confirming the constructed handler is the pre-existing `httputil.ReverseProxy` type — not via wall-clock latency benchmarking.
23. The system shall require and validate `OLLAMA_URL` only when `UPSTREAM_BACKEND=ollama` (the default); when `UPSTREAM_BACKEND=openai`, `OLLAMA_URL` shall not be required at config load. This is symmetric with FR-5's requirement that `UPSTREAM_URL` is required and validated only when `UPSTREAM_BACKEND=openai`.
24. The system shall optionally accept an `UPSTREAM_API_KEY` config value. When non-empty, the system shall send it as an `Authorization: Bearer <value>` header on every request to the OpenAI-compatible upstream. When `UPSTREAM_API_KEY` is empty or unset, no `Authorization` header shall be sent (an `Authorization: Bearer` header carrying an empty value shall never be sent). The raw value of `UPSTREAM_API_KEY` shall never appear in the Broker's structured JSON logs at any log level. The system shall reject any `UPSTREAM_API_KEY` value containing a CR or LF control character at config load, failing startup with a descriptive error, to prevent HTTP header injection into the outbound upstream request.
25. When `UPSTREAM_BACKEND=openai`, the system shall honor the incoming request's `stream` field for chat/generate: a request with `stream:false` shall receive a single buffered Ollama-shaped JSON response object (not NDJSON), and a request with `stream:true` shall use the existing incremental NDJSON streaming path (FR-6, FR-8).
26. When `UPSTREAM_BACKEND=openai`, the system shall derive the Job-path token count reported via `onTokens` (FR-9) as follows: the outbound `/v1/chat/completions` request to the OpenAI-compatible upstream shall include `stream_options: {include_usage: true}` when the upstream supports it, to request a final usage block per the standard OpenAI-compatible streaming convention; the system shall additionally maintain a running per-chunk token counter as a fallback, incremented as each streamed chunk arrives, and shall use this fallback count whenever the upstream's final chunk omits the `usage` field. This is not an edge case: vLLM, this feature's primary target upstream, omits `usage` in its final SSE chunk by default unless `stream_options.include_usage` is explicitly requested.
27. When `UPSTREAM_BACKEND=openai`, the system shall reject a `/api/chat` request containing an Ollama-specific field the translator does not support (e.g., a message's `images` field for multimodal/vision input) with an HTTP 400 error naming the unsupported field, rather than silently translating the request with that field dropped.
28. When `UPSTREAM_BACKEND=openai`, Yield/preemption/priority behavior, translation, and proxying shall apply only to chat/generate (`/api/generate`, `/api/chat`) and text-embeddings (`/api/embed`) requests. Other Ollama HTTP endpoints (e.g., `/api/tags`, `/api/show`, `/api/ps`, `/api/pull`) shall not be proxied or translated by the `openai` backend; requests to them shall receive HTTP 404. (This differs from the `ollama` backend, whose reverse-proxy passes these endpoints through transparently today.)
29. When `UPSTREAM_BACKEND=openai`, `/api/generate`'s Ollama-specific `context` field (token-continuation state for multi-turn generate-mode conversations) has no OpenAI-compatible equivalent and shall not be supported — a Consumer relying on `context` for conversation continuity shall not get equivalent behavior under the `openai` backend. The `system` field, when present, shall be mapped to a system-role message in the translated request. The `template` field has no equivalent under the `openai` backend and shall be ignored.
30. The system shall pass a Consumer's requested `model` value through unchanged (no translation or mapping layer) to the upstream's `model` field, under either backend. The Broker operator is responsible for ensuring the OpenAI-compatible upstream's served model names match what Consumers request; a mismatch surfaces as an upstream error, handled per FR-10, and is not a distinct failure mode this feature must handle specially.

## Non-functional requirements

- The `openai` backend's request/response translation must not buffer a full streaming response before forwarding — translation happens per-chunk, preserving the streaming latency profile Consumers see today.
- Config validation errors (invalid `UPSTREAM_BACKEND`, missing/invalid upstream URL for the selected backend) must fail Broker startup with a clear, actionable error message, consistent with how `OLLAMA_URL` validation fails today — never fail silently or fall back unexpectedly to a different backend.
- No new external dependency (SDK, client library) that requires network access at build time; the mock/stub OpenAI-compatible server used in tests must run fully in-process or as a local test double, with no calls to a real hosted API.

## Constraints

- Must integrate with the existing `internal/proxy/proxy.go` Fronting Proxy, `internal/job/worker.go` Job worker, `internal/job/service.go`, and `internal/config/config.go` without breaking their existing exported interfaces (`Gate`, `Yielder`, `Generator`) any more than adding the new backend seam requires.
- Must preserve the existing `internal/admin/admin.go` `HealthCheck` function signature (`func(ctx context.Context) error`) — the backend-aware reachability probe plugs into this existing contract, not a new one.
- Must preserve the existing `X-Broker-*` header/trailer names and semantics (ADR-0011) and the existing `/metrics` Prometheus metric names/labels (`broker_requests_total{class,outcome}`, `broker_job_outcomes_total{outcome}`) — this feature may add labels/metrics but must not rename or remove existing ones, or existing Grafana/alerting queries break.
- Must preserve the image-embedding embed lane (`INFINITY_URL`, `internal/proxy.NewEmbed`, ADR-0008/0009/0013) exactly as-is; it is a separate, already-shipped feature and out of scope here, and must not be confused with this feature's text-embeddings request translation (`/api/embed`, FR-7).
- Must not require any Consumer code change — Consumers keep speaking Ollama's HTTP API to the Broker regardless of backend.
- Go ≥ 1.24, static/CGO-free binary (per README build requirements) — any new dependency must not require CGO.
- Standing up a real running vLLM instance (including any ROCm/AMD RDNA4 compatibility work) is out of scope and tracked separately; this feature is validated against a mock/stub OpenAI-compatible server only.

## Out of scope

- Standing up, configuring, or validating a real vLLM server (or any real OpenAI-compatible server) — hardware/ROCm blockers on the target GPU are tracked separately.
- The image-embedding embed lane (`INFINITY_URL`, `internal/proxy.NewEmbed`, ADR-0008) — separate CPU-only lane, untouched by this feature; not to be confused with this feature's text-embeddings request translation (`/api/embed`, FR-7).
- Running both an Ollama backend and an OpenAI-compatible backend simultaneously for different Consumers/ports in a single Broker instance — this feature is a single global backend selection (`UPSTREAM_BACKEND`), not per-port or per-Consumer backend routing.
- VRAM/model unload-on-yield for the `openai` backend — `Unload`/`LoadedModels` remain Ollama-specific; an equivalent mechanism for an OpenAI-compatible upstream (e.g. vLLM) is not implemented by this feature.
- Any OpenAI-compatible endpoint families beyond chat/generate and text-embeddings (e.g. vision/multimodal beyond what chat/generate already carries, function/tool calling, fine-tuning, assistants API, moderation).
- Migrating any existing Consumer off Ollama's API onto a native OpenAI wire contract — Consumers keep speaking Ollama's API to the Broker permanently; this feature only changes what's behind the Broker.
- Performance/throughput comparison or benchmarking between Ollama and an OpenAI-compatible backend.
- Changes to the Job submission API shape (`POST /jobs` request/response fields) — Jobs remain model/prompt/options, unchanged by backend selection.

## Acceptance criteria

1. With `UPSTREAM_BACKEND` unset, every existing test in the repo passes unmodified, and the Broker's observed behavior (proxy pass-through, Job execution, `/healthz`, headers/trailers) is unchanged from the pre-feature codebase.
2. Setting `UPSTREAM_BACKEND=bogus` (or any value other than `ollama`/`openai`) causes `config.Load()` to return a non-nil error and the Broker fails to start, with an error message naming the invalid value.
3. Setting `UPSTREAM_BACKEND=openai` without a valid upstream URL configured causes `config.Load()` to return a non-nil error, analogous to the existing `OLLAMA_URL` validation error.
4. With `UPSTREAM_BACKEND=openai` and a mock OpenAI-compatible test server standing in for the upstream, a Synchronous chat/generate request sent to the interactive port in Ollama's request shape (`stream:true`) receives a response in Ollama's response shape, streamed incrementally (verified by observing multiple flushed writes, not one final write).
5. With `UPSTREAM_BACKEND=openai` and a mock OpenAI-compatible test server, a Synchronous text-embeddings request sent to the batch port in Ollama's request shape (`/api/embed`) receives a response in Ollama's embeddings response shape.
6. With `UPSTREAM_BACKEND=openai`, a Job submitted via `POST /jobs` runs to `SUCCEEDED` against a mock OpenAI-compatible test server, and its progress reflects an increasing token count during execution (observable via `GET /jobs/<id>` or the SSE `/jobs/<id>/events` stream).
7. With `UPSTREAM_BACKEND=openai`, a Job in flight when Yield begins (mock gaming/Plex Contention) is preempted and requeues to the front of the Queue — identical to today's Ollama-backend behavior — verified by a test that triggers Yield mid-Job and asserts the Job returns to QUEUED at position 1.
8. With `UPSTREAM_BACKEND=openai`, an interactive request that preempts a running batch Job past `BROKER_BATCH_QUANTUM` produces the same preemption/requeue outcome as the `ollama` backend does today.
9. With `UPSTREAM_BACKEND=openai` and the mock upstream reachable, `GET /healthz` returns `200 {"status":"ok"}`. With the mock upstream unreachable (connection refused or timeout), `GET /healthz` returns `503` naming the upstream as the failed dependency.
10. With `UPSTREAM_BACKEND=openai`, every Synchronous response still carries `X-Broker-Request-Id`, `X-Broker-Wait-Ms`, and `X-Broker-Status` (header and, on streamed responses, trailer) with the same semantics as the `ollama` backend.
11. With `UPSTREAM_BACKEND=openai`, `/metrics` continues to expose `broker_requests_total{class,outcome}` and `broker_job_outcomes_total{outcome}` with existing label values (`served`, `deferred`, `preempted`, `succeeded`, `failed`, etc.) unchanged in name/shape.
12. A request to the image-embedding embed lane (`INFINITY_URL`/`BROKER_EMBED_ADDR`) is unaffected by `UPSTREAM_BACKEND`'s value — the embed lane's behavior is identical whether `UPSTREAM_BACKEND` is `ollama` or `openai`.
13. Simulating an OpenAI-compatible upstream error (mock server returns non-2xx or a mid-stream error payload) produces a Job `FAILED` state (after exhausting `BROKER_JOB_MAX_ATTEMPTS`) or a Synchronous `503`/error response consistent with how an equivalent Ollama upstream error is handled today.
14. No test in the added `openai` backend test suite makes a network call to a real, non-local OpenAI-compatible API — all tests run against an in-process mock/stub server.
15. A test asserts that when `UPSTREAM_BACKEND=ollama`, the constructed request handler is the same `httputil.ReverseProxy` type produced by `proxy.New()` pre-feature (a type assertion or equivalent code-path check) — not a wall-clock latency measurement.
16. Setting `UPSTREAM_BACKEND=openai` with `OLLAMA_URL` unset does not cause `config.Load()` to fail — only `UPSTREAM_URL` is validated in this mode. Setting `UPSTREAM_BACKEND=ollama` (or leaving it unset) with `OLLAMA_URL` unset/invalid causes `config.Load()` to fail, matching today's behavior.
17. With `UPSTREAM_API_KEY` set to a non-empty value, a request to the mock OpenAI-compatible upstream includes an `Authorization: Bearer <value>` header. With `UPSTREAM_API_KEY` unset or empty, no `Authorization` header is sent. Broker logs at any level, captured during a request that used a non-empty `UPSTREAM_API_KEY`, do not contain the raw key value. Setting `UPSTREAM_API_KEY` to a value containing a CR or LF character causes `config.Load()` to return a non-nil error and the Broker fails to start.
18. With `UPSTREAM_BACKEND=openai`, a chat/generate request with `stream:false` receives a single buffered Ollama-shaped JSON response (one write, not NDJSON). A request with `stream:true` continues to receive incrementally flushed NDJSON chunks (AC-4).
19. With `UPSTREAM_BACKEND=openai` and a mock upstream that omits the `usage` field on its final SSE chunk (replicating vLLM's default behavior), Job token-count progress still increases and reaches a correct final count, derived from the per-chunk fallback counter. A separate test confirms the outbound request to the mock upstream includes `stream_options: {include_usage: true}` in the request body.
20. With `UPSTREAM_BACKEND=openai`, a `/api/chat` request whose message includes an `images` field receives an HTTP 400 response, and no request is forwarded to the mock upstream.
21. With `UPSTREAM_BACKEND=openai`, requests to `/api/tags`, `/api/show`, `/api/ps`, and `/api/pull` each receive HTTP 404. The same requests against `UPSTREAM_BACKEND=ollama` continue to pass through to the mock/real Ollama upstream unchanged.
22. With `UPSTREAM_BACKEND=openai`, an `/api/embed` request with multiple input strings receives a response whose embedding vectors are in the same order as the request's inputs, verified by a test using distinguishable per-input mock embeddings.
23. With `UPSTREAM_BACKEND=openai`, an `/api/generate` request including a `context` field is accepted but produces no stateful continuation behavior (the field has no effect); a request including a `system` field produces a system-role message in the translated upstream request; a `template` field, if present, is ignored without error.
24. With `UPSTREAM_BACKEND=openai`, the `model` value sent to the mock upstream in a translated request is byte-identical to the `model` value the Consumer supplied in its Ollama-shaped request.
